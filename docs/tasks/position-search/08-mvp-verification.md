### Reproducible benchmark measurements (fixture-only)

Measured on a GitHub-hosted Linux x64 runner: **AMD EPYC 7763 64-Core Processor** (4 logical CPUs exposed), **15.615 GiB RAM**, Node.js **22.22.0**, better-sqlite3. These are one observed run, not promised limits.

| Index step | Observed time / size |
| --- | ---: |
| Explicit schema install on backup | 2.711 ms |
| Initial full build (240 attempted; 239 valid, 1 failed) | 438.365 ms |
| Incremental build (239 skipped; 1 invalid retried) | 3.510 ms |
| Forced full rebuild (240 attempted) | 426.819 ms |
| Archive size before index | 520,192 bytes |
| Archive size after index | 847,872 bytes |
| **Additional SQLite footprint** | **327,680 bytes (320 KiB)** |

Search measurements use **80 synchronous `ChessArchive.searchByPosition` samples per FEN**, after **10 warm-up searches** per FEN; p50 and p95 are nearest-rank percentiles. They include SQL, typed filtering, coverage evaluation and API object assembly, **not** IPC or browser rendering.

| Query | p50 | p95 | Distinct matching games | Stored occurrences | Excess duplicate occurrences |
| --- | ---: | ---: | ---: | ---: | ---: |
| Orthodox starting position | 2.767 ms | 3.262 ms | 238 | 262 | 24 |
| Common opening (`1.e4 e5 2.Nf3 Nc6`) | 2.084 ms | 2.765 ms | 96 | 96 | 0 |
| Transposed middlegame (20 plies) | 1.914 ms | 3.104 ms | 48 | 48 | 0 |
| Rare rook/pawn position (`1.a4 h5 2.Ra3 Rh6`) | 1.707 ms | 2.093 ms | 24 | 24 | 0 |

The root query's **262 occurrence rows** collapse to **238 unique games**, proving deterministic per-game deduplication; two middlegame move orders return the same searched position without a named-opening filter. The benchmark checks these raw/unique counts against actual API totals and records `coverage.status='partial'` for every query because of the deliberately invalid score. A zero-match result under such coverage is explicitly not conclusive.

**Observed SQL plans:** the key lookup uses `SEARCH position_keys USING COVERING INDEX sqlite_autoindex_position_keys_1 (zobrist_hash=? AND exact_key=?)`; the occurrence step uses `SEARCH o USING INDEX game_position_occurrences_position (position_id=? AND is_mainline=?)` plus primary-key joins for index state and games, a materialized `position_hits` window, and a temporary B-tree for the remaining order terms. Both indexed lookups are asserted in the benchmark script.

### Reproduction and recovery

```sh
npm test
npm run build
xvfb-run -a npm run test:desktop     # Linux CI / other graphical desktop session
npm run benchmark:positions -- --games 240 --samples 80
npm run benchmark:positions -- --database /path/to/schema7.sqlite3 --samples 80
```

The last command, for an optional real archive, opens the input **read-only**, uses SQLite `backup()` to create a temporary working copy, measures install/build/rebuild/search against that copy, verifies the source hash did not change and cleans the copy up. The default command generates a fixture instead. Use `npm run positions -- status --database COPY` to inspect index completion, `build` to resume stale/unindexed rows, and `rebuild --dry-run` then `rebuild` to refresh derived data. Bad PGNs need source correction/reimport; if the optional index is incompatible, make a new SQLite backup from the untouched source and re-run `init → build → status`. README and `docs/database.md` describe mainline-only scope, safe backups and explicit recovery.
